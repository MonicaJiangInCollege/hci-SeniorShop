# 迭代案例：结算语音确认

## 问题（第一轮测试）

| 指标 | 第一轮 |
|------|--------|
| T3 成功率 | 5/6（83%） |
| T3 误操作 | P5 未理解 pending，以为已付款 |
| 访谈 | 「去结算」后直接提交，缺少「我说对了才提交」的安全感 |

**根因**：`processVoiceCommand` 中「去结算」立即调用 `paySilent()`，无二次确认，违反容错性原则。

## 改动（第二轮）

1. **纯语音模式**下，「去结算」改为：
   - 播报购物车摘要：「您选了 N 件，合计 X 元」
   - 提示：「请说确认提交来完成下单」
   - 仅识别「确认提交」「确认」「好的提交」后才创建订单

2. **提交成功后 TTS**：「已经告诉儿子了，等着付就行」

3. **视觉**：语音模式面板显示当前步骤「等待您说确认提交」

## 复测结果

| 指标 | 第一轮 | 第二轮 |
|------|--------|--------|
| T3 成功率 | 83% (5/6) | **100% (6/6)** |
| T3 平均耗时 | 77s | 82s（+5s，可接受） |
| pending 理解度 (1–5) | 3.8 | **4.5** |
| 误提交 | 1 次 | **0 次** |

## 结论（答辩用）

> 可用性测试发现语音结算缺少确认步骤 → 增加「确认提交」门槛 → T3 成功率提升至 100%，体现 UCD 闭环。

## 代码对应

- `awaitingCheckoutConfirm` 状态
- `processVoiceCommand` 结算分支
- `paySilent()` 仅在确认后调用
